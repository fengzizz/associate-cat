# plan Code Handoff

## 适用场景

- 先读取同目录 `plan-implementation.md`；本文件只补充 plan、任务和代码之间的映射细节。
- 用户可见的映射、阻塞和核对默认属于对话表面并使用 `Interaction Language`；用户明确要求把对应结构写入某个 Plan 或文档时，才使用该文档的 `Output Artifact Language`。解析输入 Plan 时不得把某个本地化标题字符串作为唯一主键，应继续使用固定协议、ID、结构和全文语义。
- 输入可以是当前对话中的计划，也可以是用户指定的持久 plan、任务拆分、评审结论或 issue 列表。
- 目标是将 `Current Plan` 稳定落地为可验证代码，而不是在代码阶段重新产出一套新设计。
- 同时适配粗略计划和细致计划；不要依赖固定标题、章节名或模板。

## 计划粒度处理

先判断输入属于哪一类：

- **可直接施工的 plan**：目标、限制、任务、边界、行为后果和验证信息足够，相关 Task 为 Ready。
- **可提炼边界的粗略计划**：只有目标、若干步骤、限制或少量点名对象。
- **参考性文档**：分析、总结、方案比较、复盘或实现总结。

处理规则：

- 可直接施工时建立实现清单、本轮任务范围和本轮允许修改的范围，再按 `plan-implementation.md` 实施。
- 粗略计划只在目标和设计已经唯一确定时提炼暂定修改集合；会改变语义的缺口导致 `Current Plan` 无法施工时，停止当前实施批次并报告问题，不直接写代码，也不在 Code 阶段补充设计。
- 参考性文档只有在用户当前明确要求按其落地，且可执行目标、限制和边界成立时才进入实施。
- 不依赖标题名，从全文提取目标、验收、禁止项、风险、点名文件或对象、行为变化、依赖顺序、兼容要求和显式排除项。

## 执行步骤

### 1. 解析 plan 并建立任务清单

- 提取 `Document Status`、`Design Readiness`。
- 提取每个 Task 的 ID、`Task Readiness`、目标、约束、依赖、完成标准、实现卡片和验证卡片，以及对应当前设计、有效的 Decided 记录或带来源约束。
- 只调度属于用户当前实施目标、Ready 且不依赖 Not Ready 上游的 Task。
- 把 Task ID 视为稳定身份，不视为固定执行序号；按真实产物和接口合同依赖重建拓扑执行序列。
- 显示顺序存在前向依赖时只调整本轮执行队列并报告；依赖未就绪、循环无法消解、Task 后中间状态不安全或需要新的设计决策时，停止当前实施批次并报告阻塞，不继续调度其他 Task。
- 区分“plan 明确要求”和“实现时推断得到”的内容；后者默认不进入修改范围，除非能够从当前设计唯一推导且不改变边界。
- 发现 Open 决策、阻塞性事实缺口、Not Ready Task、实现信息缺口或 plan 与当前事实冲突时，将受影响 Task 视为不可施工并停止相关写入。
- Open 决策只作为阻塞来源，不作为代码实施依据；Decided 记录只有与当前设计一致时才能进入施工映射。

### 2. 建立 change point 与代码映射

- 将每个 change point 按 `对象 + Action + 语义效果` 映射到唯一 Task；同一对象跨 Task 时，动作和语义效果不得重叠，依赖必须明确。
- 将实施 Task 的跨文件、接口和技术层操作映射为有序代码步骤。
- 将独立 Validation Task 映射为验证对象、步骤、证据和通过标准，不生成代码步骤，本轮允许修改的范围为空。
- 在首个代码写入前完成全批次预检。逐项消费当前设计、有效的 Decided 记录或带来源约束、Target、Task、change point、实现/验证卡片、验收条件和验证矩阵，为每项记录预期文件与对象、预期行为和验证项；不得只把一个 Task 粗略映射到一个文件就视为消费完成。
- 将计划元素标记为 `已映射 / 不适用（附依据） / 阻塞`。无法定位、无法关联 Task 或仍需设计判断时停止写入。
- 对话中只输出紧凑任务队列：Task ID、Ready 状态、依赖、本轮实施范围和阻塞；内部消费清单不必完整铺到对话中。

### 3. 建立边界

按以下优先级建立本轮允许修改的范围：

1. 显式文件列表、In Scope、Out of Scope。
2. 文档点名的类、函数、模块、配置项或其他对象。
3. 实现步骤隐含的直接修改点及其最小必要依赖。
4. 只有通用目标时，通过项目搜索得到的最小实现面。

- 为每个实施 Task 记录允许编辑的文件、对象、函数或配置项；Validation Task 的集合为空。
- 计划较粗略时标为“暂定本轮允许修改的范围”，只覆盖当前目标的最小实现面。
- 缺失信息影响行为、所有权、状态、生命周期、接口顺序、默认值、控制流、失败处理或验证时，停止当前实施批次并报告缺口；不要把它包装成局部细节，也不要在 Code 阶段补充设计。
- 实施中需要集合外修改时，先停止并使用超范围阻塞报告。

### 4. 按实施批次落地

- Task 起始门禁、连续实施、局部验证、Validation Task、进度和停止条件遵守 `plan-implementation.md`。
- 每个实际代码步骤继续携带其 plan 元素映射和本轮允许修改的范围。
- 局部验证失败时，只对能够由当前设计唯一推导修正方式的实现偏差回到原 Task；暴露设计缺口时，停止当前实施批次并报告问题。
- plan 新增需求或改变 Task 语义时，停止当前实施批次并报告哪些设计决策记录、change point、依赖或 Task 已不足以支持实施。Code 阶段不得更新这些计划内容；用户后续提供新的实施指令后，重新建立代码映射、本轮实施范围和本轮允许修改的范围，旧映射不得覆盖新增语义。

## 批次双向核对

批次完成后按任务风险和复杂度核对；小型任务可以压缩输出，但不能省略范围、行为和验证结论。

### plan 到代码

- 沿消费清单确认结构、数据归属、调用或状态顺序、失败、清理、回退、边缘路径和验证项落到准确文件与对象。
- plan 有验证矩阵时逐项收口；没有时按关键验收场景收口，不补造无来源验证编号。
- 正向核对结果只使用 `符合 plan / 结构偏离 / 行为或边缘路径缺口 / 未落地`，不把计划外实现混入正向结果集合。
- 验证状态只使用 `已验证 / 失败 / 未验证 / 阻塞 / 不适用（附依据）`；存在失败、未验证或阻塞时不得宣称闭环。

### 代码到 plan

- 检查本轮每个新增或修改的类、成员、helper、接口、分支、状态和调用关系能否回溯到 Task、当前设计和有效的 Decided 记录或带来源约束。
- 无法回溯的实现分类为 `结构偏离` 或 `计划外实现`，不得用“实现细节”掩盖。
- 反向核对结果只使用 `可追溯 / 结构偏离 / 计划外实现`，并记录实际落点、plan 来源和影响。

### 核对阶段的修复边界

- 严格属于本轮实施范围、且能从当前设计唯一推导的实现偏差可以在当前批次修正。
- 新语义、新文件、新模块、公共接口、批量调用方、较大重构、系统性清理或额外设计判断不在核对阶段顺手落地。
- 测试通过、问题容易处理或实现方便都不能扩大本轮实施范围。
- 未立即处理的问题进入阻塞与未完成项，写清影响、不改原因，以及继续实施所缺少的输入或边界。

## 汇总交付

- 输出“计划项 → 代码改动或验证执行 → 验证结果”的映射。
- 输出 plan 与代码的双向核对结论；没有偏离时也明确记录。
- 标出未完成项、阻塞原因，以及继续实施所缺少的事实、权限或明确边界。
- 单独列出计划外影响面，不把建议伪装成本轮已处理内容。
- 默认使用适合窄窗口的结构化列表；信息非常规整时才使用表格。

```md
## plan → 代码正向核对
### TASK-001

- 实际代码落点：

- <实际对象> → TASK-... / Decision-...：可追溯
- <意外对象>：结构偏离 / 计划外实现

## 验证闭环
- 验收项：已验证 / 失败 / 未验证 / 阻塞 / 不适用（附依据）
- 总结：已闭环 / 未闭环

## 阻塞与未完成项
- 只记录本轮未完成内容、阻塞事实、影响范围和继续实施所缺少的输入或边界；不在 Code 阶段补充新的设计或 Task。
```

## 最低验收标准

- 每个实施 Task 对应至少一个代码改动点；Validation Task 对应明确验证目标和结果，但没有代码改动点。
- 首次写入前已经为当前实施批次建立逐元素消费清单；当前设计、有效的 Decided 记录或带来源约束、Target、Task、change point、实现/验证卡片、验收项和验证矩阵均已映射、标记不适用依据或阻塞。
- 每个被修改文件、对象、成员、helper、接口、分支、状态和调用关系都能正向、反向回溯到 Task、当前设计、有效的 Decided 记录或带来源约束；仅文件级映射不足以证明闭环。
- 每个代码改动点都有行为变化说明。
- 每批次至少有一条可执行验证记录。
- 验证矩阵中的每一项都有明确状态；失败、未验证或阻塞时不宣称闭环。
- 剩余风险、计划外影响和未验证项可追溯、可继续推进。
