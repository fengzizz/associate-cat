# 前置代码分析

仅在需要校准“前置代码分析”章节的写法、压缩方式与常见误区时读取本文件。
本文件不负责重新定义 relevance level；对象分级与最低分析深度以 `analysis-relevance-grading.md` 为准。
当第3节已经足够清晰、紧凑、分层明确时，不必额外读取本文件。

## Goal

- 高重要度分析必须有足够判断密度，但不得扩写成源码阅读笔记。
- 将大量源码阅读压缩为“支撑本次方案决策所需的最小充分结论”。
- 明确区分三类内容：
  - 代码事实：源码中已经存在的结构、行为、状态或调用关系；
  - 分析推断：基于代码事实得出的职责、意图、风险或影响判断；
  - 方案约束：本次方案必须遵守、复用、避开或刻意改变的要求。
- 禁止把代码事实、分析推断和方案约束混在同一段里模糊表达。
- 主动过滤与本次方案无直接关系的源码细节、旁支逻辑和实现噪音。

## Scope

- 用于校准第3节的写法、压缩方式和常见误区。
- 不用于重新决定对象属于 `Low / Medium / High / Very High` 中的哪个等级。
- 不用于替代 `SKILL.md` 的主工作流或输出模板。

## Core Rule

- 先分析充分，再输出压缩结果。
- 最终计划里的第3节只保留会影响方案边界、复用判断、风险判断、验证路径的内容。
- 不把探索过程、背景铺垫、完整调用链走读原样写进正文。
- 直接约束方案的现状职责。
- 容易被误判的关键时序、状态流、初始化顺序。
- 明确的扩展点、复用边界、不可改动边界。
- 验证路径、失败观察点、回归关注点。

## What To Drop By Default

- 与本次方案无直接关系的背景知识。
- 只为证明“看过代码”而列出的模块名或文件名。
- 逐行解释源码。
- 与后续方案无直接关系的次要 helper 细节。
- 在多个章节重复出现的同一条约束、风险或边界。

## 汇总代码上下文

分析源码时，在必要的时候需要及时汇总代码上下文，使得零散代码的相互联系更清晰。

基本汇总思路：
- 走读相关模块、核心类和调用链。
- 标记可复用点、技术债、风险点；Bug 任务需额外标记最可能的故障链路。
- 如果用户主动告知了一些注意事项，如果这些注意事项和计划相关，需要明确记录在执行计划中，作为参考。
- 对于相关性高或极高的分析对象，不能只写“可复用”或“需要对标”。

## Fact / Inference / Constraint

- `代码事实`：能从当前实现直接读出的行为、职责、状态、顺序、接口。
- `分析推断`：基于当前实现得出的原因判断、风险判断、可行性判断。
- `方案约束`：这些事实和推断对本次设计施加的“必须保留 / 不要误改 / 可以复用 / 需要规避”。

写作时：

- 以 `代码事实` 和 `方案约束` 为主。
- `分析推断` 只保留真正影响决策的部分。
- 设计口径与实现建议放到“实现方案”以后。

## Positive Pattern

- 结论先行：先说“这个对象约束了什么”，再列少量关键支撑点。
- 高密度表达：优先写职责、顺序、边界、风险，不写背景铺垫。
- 一个对象一组结论：避免同一对象在多个小节被反复拆散描述。
- 把本文件当成写法原则，而不是固定句式模板。

## Negative Pattern

- 只列文件名，不说当前行为和职责。
- 只写“可复用”或“需要对标”，但不说明复用什么、对标什么。
- 把完整阅读过程直接粘贴到第3节。
- 在第3节提前写实现建议，导致前置分析和方案混在一起。
- 同一条风险或边界在前置分析、实现方案和后置评估中重复出现。
- 机械照抄本文件或 `analysis-relevance-grading.md` 的原句，导致计划正文看起来像规则摘录而不是任务分析。
