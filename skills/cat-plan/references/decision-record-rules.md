# 设计决策记录规则

本文件只负责正式 plan 中设计决策记录的准入、决策责任、状态和当前结果收敛。事实分析、存盘授权、Task 拆分和输出模板继续由各自引用负责。

## 标准术语

- 方案分歧：至少两个有事实依据且能够真实落地的方案之间，存在会改变结果的差异。
- 决策事项：需要在真实方案分歧中作出选择的完整问题。
- 备选方案：决策事项下可被选择的真实可行方案。
- 推荐方案：需要用户作出决策时，AI 基于现有证据给出的优先建议。
- 决策结果：对决策事项已经生效的选择。
- 决策记录：保存决策事项、状态、主体、依据、结果和影响的 plan 内记录。
- 决策主体：对决策结果负责的一方，只使用 `AI` 或 `User`。
- 决策依据：支持决策结果的事实、约束、取舍和推导理由。
- 事实缺口：会影响方案但暂时无法从项目、工具、权威资料或合理调查中获得的事实。
- 用户介入：用户补充不可发现事实，或作出只能由用户负责的决策；它不是 plan 状态。

`Decision-001`、`Decision-002` 是 `Current Plan` 内的决策记录 ID。正文统一使用“决策事项、备选方案、推荐方案、决策结果、决策记录、决策主体、决策依据”，不使用缩写代替这些概念。

## 加载边界

出现以下任一情况时读取本文件：

- 当前范围可能存在两个以上会改变结果的真实可落地方案，需要判断是否建立设计决策记录。
- `Current Plan` 已包含 `Decision-...`，需要核对状态、当前结果或下游映射。
- 上下文压缩、会话恢复或新会话接管后，需要恢复当前有效决策结果及其下游映射。

纯事实分析、Bug 根因定位、代码说明、唯一方案推导和格式整理不读取本文件，也不建立设计决策记录。

## 决策形成前提

先区分事实、推断和事实缺口。关键事实链未闭合时，不把推荐方向写成当前设计。

- Bug：先闭合现象、触发条件、错误状态、传播路径和根因，再比较覆盖同一根因与范围的总体修复路线。事实和约束只支持一条合理路线时，记录唯一推导依据，不建立决策记录。
- 新需求或重构：围绕完整行为合同、职责边界或验收结果识别方案分歧，不按类、字段、状态、生命周期、失败路径或验证项机械拆分决策事项。
- 总体路线确定后，只有仍存在会改变结构、行为、兼容与回退、主要风险或验证结果的独立分歧时，才建立新的决策记录。

## 准入与分流

只有同时满足以下条件，才建立设计决策记录：

1. 当前事项至少存在两个有事实依据且能够真实落地的方案。
2. 不同方案会改变目标行为、职责或架构边界、兼容与回退、主要风险或验收结果。
3. 该差异不能由已确认事实、带来源约束、项目规则或已生效的上游设计唯一推导。
4. 该事项能够作为完整单元独立作出选择。

分配编号前完成以下分流：

- 用户已经明确且不存在开放取舍的要求，记录为带来源约束，不建立决策记录。
- 事实和约束只支持一条合理路线时，直接写入当前设计并记录推导依据。
- 只影响局部写法且不改变行为、职责边界、兼容、主要风险或验收的实现细节，由实施阶段在当前设计约束内处理。
- 事实不足时记录事实缺口，不把未知事实包装成决策事项。
- 明确排除项进入 `Out of Scope`，不建立决策记录。

## 决策责任

### AI 作出决策

当决策事项同时满足以下条件时，AI 必须完成比较并直接作出决策：

- 事项属于用户已限定目标和范围内的技术设计。
- 所需事实能够从项目、工具、权威资料和已知约束获得。
- 可以依据正确性、现有架构、兼容性、复杂度、性能、可维护性、验证能力和项目惯例判断取舍。
- 结果不替用户定义业务目标，不扩大范围，也不要求用户承担新的重大风险。

AI 作出决策后，将记录标记为 `Decided`，填写决策结果、决策主体 `AI`、决策依据和影响范围，并把结果同步为唯一当前设计。多个技术方案都可行本身不是请求用户选择的理由。

### 用户补充事实

当缺失信息无法从项目、工具、权威资料或合理的非修改性调查中发现，并且该信息会改变目标、范围、行为、架构、风险接受或验收时，请求用户补充最小必要事实。

该缺口记录为事实缺口，不建立 `Open` 决策记录；只有事实补齐后仍存在真实方案分歧时，才继续判断决策责任。受影响范围保持 `Not Ready`，无关范围可以继续收敛。

### 用户作出决策

当多个真实可行方案的差异主要取决于以下任一内容时，决策主体必须是 `User`：

- 用户定义的业务目标或产品语义。
- 无法从现有设计推导的主观体验偏好。
- 重大风险接受，包括破坏性兼容、数据迁移、不可逆操作、安全或隐私后果、明显成本增加。
- 超出当前请求的范围扩张。
- 权威来源冲突且不同取舍会改变验收优先级。

请求用户前，AI 必须先完成可发现事实调查，把问题收敛为一个或少量最小决策事项，提供二至三个简短、互斥的备选方案，说明推荐方案及主要影响，并写出用户需要回答的最小问题。对应记录保持 `Open`，受影响范围保持 `Not Ready`。

不得因技术工作复杂、存在多个实现细节、希望获得形式性确认、缺少信心或计划仍可由工程标准判断而要求用户介入。

## 粒度与当前记录

- 多个维度必须共同变化，或者交叉组合没有独立语义时，合并为一个决策事项。
- 存在有意义的交叉组合，且一个选择可以独立变化时，保持不同决策事项。
- 现有记录已经覆盖同一事项边界时，更新原记录和全部下游映射，不机械追加编号。
- 补充证据、解释语义或记录唯一派生结果时，更新原记录和当前设计，不新增编号。
- 事项边界实际改变，不能继续表示同一个完整问题时，才建立新的 `Decision-...`。

## 状态与当前快照

- `Decision Status` 只使用 `Open / Decided`。
- `Open` 只用于必须由用户作出决策、但用户尚未提供结果的真实方案分歧。
- `Decided` 表示当前决策结果已经由 `AI` 或 `User` 作出，并已同步到当前设计。
- 决策记录 ID 使用 plan 内局部三位顺序号：`Decision-001`、`Decision-002`。
- 标题使用“决策对象 + 决策内容”，直接说明需要决定什么。
- `Current Plan` 不保存旧决策结果、被替代记录、重开摘要或普通修订过程；需要复盘时读取聊天记录、版本历史或旧文件。
- 同一决策事项发生变化时更新原记录和全部下游映射；事项边界实际改变时才建立新的 `Decision-...`。

## Current Plan 与上下文恢复

已有 `Current Plan` 时，把它作为当前决策索引。新增或更新记录前：

1. 读取当前 `Document Status`、`Design Readiness` 和相关决策记录的完整块。
2. 读取对应当前设计、Target、Task 和验证映射。
3. 建立“当前问题 → 带来源约束 / 事实缺口 / 现有 Decision / 当前设计”的最小映射，再判断是否需要编号或更新原记录。

上下文压缩后应从 `Current Plan` 恢复，不把模型上下文摘要当作完整记录。工具输出被截断时，定向补读相关块；调用过读取工具不等于已经消费完整记录。

用户反馈或新证据先分类为事实纠正、明确新增约束、当前决策结果修正、事项边界改变或独立新事项。分类完成前不得直接追加编号。

## 下游收敛与就绪检查

- 所有 `Decided` 记录都必须与当前设计一致；冲突时先重新分析事实并修正当前设计，不能让 Task 反向决定设计。
- `Open` 记录只保留帮助用户作出决策所需的简短选项和推荐，不写入当前设计、Target 或正式 Task。
- 阻塞性事实缺口和 `Open` 决策分别记录；二者都不进入受影响范围的 Target 和正式 Task。
- 决策结果闭合后，将记录更新为 `Decided`，并同步当前设计、Target、Task 和验证，删除已经失效的选项和过程内容。
- 当前 Ready 范围不得受 `Open` 决策或阻塞性事实缺口影响；局部阻塞时只让受影响范围保持 `Not Ready`，整体可标记为 `Partially Ready`。
- 每个 Task 都应能追溯到当前设计、有效的 `Decided` 记录或带来源约束。
