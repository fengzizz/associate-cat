# 计划收敛与任务拆分规范

本规范定义使用 `cat-plan` 规划 Bug、新需求、行为或性能修改、工具开发与系统重构时的通用流程。项目规则在本规范上追加领域知识，不得降低这里的证据、范围、决策追溯和就绪门禁。

## 适用范围

- 适用于程序源码、工具、配置和其他可实施的项目开发任务。
- 简单问答、只读代码说明和不改变语义的机械操作不要求生成完整 plan，但仍不得越过用户给定范围。
- 已有按主 `SKILL.md` 建立身份的 `Current Plan` 时，先核对其当前证据、状态和未决项；仓库中存在 Plan、标题或主题相似、文件名匹配，都不能把历史或 source Plan 变成 `Current Plan` 或 `Current Plan Document`，任务涉及的其他文档也不能建立该身份；不要因为文档标题叫“计划”就假定其可以实施或写回。

## 规划责任

- AI 在限定任务内连续完成必要事实调查、需求校正、方案比较、设计决策、任务拆分和计划评估，不逐个技术决定等待用户选择。
- 当前设计正文只呈现一套现行方案。只有真实方案分歧才进入设计决策记录，且备选方案只保留到足以支持决策，不把 plan 变成头脑风暴记录。
- 用户监督主要发生在 Plan 审阅之后。Direct User Request Prose 明确反馈已经建立身份的 `Current Plan` 时，只重新分析受影响范围并维护同一逻辑 Plan；需要存盘时写回已经建立的 `Current Plan Document`。未指定的历史或 source Plan 不因反馈主题相同而获得任一身份。
- 未知事实、权威证据冲突、范围扩张、无法闭合的验证条件或必须由用户定义的业务偏好不能被虚构；继续完成证据允许的分析，分别记录事实缺口或 Open 决策，让受影响范围保持 `Not Ready`，并列出最小必要输入。
- 规划责任不扩大用户请求。用户只要求方案或评审时，在计划交付后停止，不进入实施。

## 共设计基础与决策路由

1. 基于当前项目事实建立与任务直接相关的事实模型。
   - Bug：现象、触发条件、错误状态、传播路径、根因。
   - 新需求：目标行为、当前流程、能力缺口、候选结构。
   - 重构：当前职责与依赖、具体结构问题、必须保持的不变量、候选边界。
2. 判断是否同时存在两个以上会改变结果的真实可落地方案；不成立时直接形成当前设计或记录事实缺口。
3. 存在真实方案分歧时，判断决策责任。技术设计且可由事实与工程约束判断时由 AI 直接决定；必须由用户定义的业务语义、主观偏好、重大风险接受或范围扩张决定结果时才请求用户作出决策。
4. 只有需要用户作出决策的范围可以保留 `Open`；阻塞性事实缺口单独记录。二者都不进入受影响范围的 Target 和正式 Task。
5. 当前结果闭合后，将 Decided 记录、当前设计、Target、Task 和验证同步为一套一致方案。
6. 进入 `Ready` 前执行覆盖闭环：把目标和后续新增需求逐项映射到带来源约束、当前设计、Target、Task 和验证。排除项记录为带来源的 `Out of Scope`。

## Current Plan 必须承载的内容

正式 plan 至少包含：

- `Document Status`：`Current Plan` 快照是否完整。
- `Design Readiness`：全部或部分任务是否可以实施。
- 应用场景、使用前提、目标、范围、项目事实、关键假设、当前设计、适用时的设计决策记录、风险和验证策略。
- 按依赖顺序拆分的正式 Task；每个 Task 映射当前有效设计，以及适用时有效的 Decided 记录或带来源约束。
- 对源码实施 Task，提供准确文件或定位方法、symbol 或对象、单一责任、行为后果、局部验证和重新设计停止条件；只有实际需要时展开输入输出、伪代码、失败清理、并发或联网考虑。

状态约束：

- 只有部分范围独立收敛时，只为该部分生成 Ready Task；受 Open 决策或阻塞性事实缺口影响的范围保持 Not Ready，并将整体标记为 `Partially Ready`。

## 任务拆分

- 只为设计思路有效且通过覆盖闭环的范围生成正式 Task。
- 任务拆分只使用 `task-decomposition-method.md`，不读取配置选择第二套方法，也不在规划中混合临时策略。
- Task ID 是稳定身份而非执行位置；按真实依赖排序，保证每个 Task 完成后处于可安全验证的中间状态。
- Task 被合并、拆分或改变语义时，重新建立受影响 change point，并重新评估依赖、实现信息和 Ready 状态；稳定 ID 不延续已经改变的语义边界。
- 独立 Validation Task 只负责明确的验证目标、依赖、步骤和结果，允许修改集合为空，不能借验证之名补写实现。

## 对话与本地存盘

- `Current Plan Document` 身份、Plan 文档动作、目标分配和恢复门禁由主 `SKILL.md` 及其直接加载的 `plan-persistence.md` 定义；本 reference 不从文件搜索、标题、主题、内容相似度或其他任务文档建立第二套判断。
- 当前活动规划任务没有 `Current Plan Document` 时，默认在对话中维护 `Current Plan`；Direct User Request Prose 明确要求 Plan 文档、保存或写入本地 Plan 时，再按主契约处理首次存盘。
- 用户明确要求维护已经建立身份的 `Current Plan` 时，新的事实、分析、当前设计和反馈仍属于同一逻辑 Plan；需要写回时只更新同一 `Current Plan Document`，不创建平行副本。
- 被提供、发现或引用的 source / historical Plan 默认保持只读；用户要求根据它生成新 Plan 时，source 文件保持不变。
- “开始实现”“按方案落地”或任务复杂本身不授权创建、发现或写回 Plan 文件。
- 保存或同步时移除下一步回复示例、讨论邀请、普通修订过程和其他会话脚手架；`Current Plan` 只保留当前有效内容。
- 用户明确要求实施指定 Plan 或 Task 时，由当前请求确定交给 Code 阶段的目标范围；该请求不写入 Plan 状态。Code 阶段仍须核对当前事实、Ready、未决项、依赖、实现信息和允许修改集合。

## 计划评估

进入 Ready 前检查：

1. 当前项目事实仍支持方案依据。
2. 当前 Ready 范围不存在 Open 决策或阻塞性事实缺口。
3. 每个 Task 都能追溯到当前设计、有效的 Decided 记录或带来源约束。
4. Task 的目标、边界、依赖、行为后果、局部验证和停止条件足以施工。
5. 所有 in-scope 关键修改点均映射到 Task，或明确标记为 Out of Scope、Warning 或 Future Work。
6. 验证策略能够区分通过、失败、未验证、阻塞和不适用。

任一项不成立时，只让受影响范围保持 Not Ready；继续完成其余证据允许的分析，不用形式性兜底掩盖缺口。
