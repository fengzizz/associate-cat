# Associate Cat

[在 skills.sh 查看](https://skills.sh/fengzizz/associate-cat)

[English](README.md)

Associate Cat 是一组面向软件开发的双 Skill 工作流。你可以先用自己的话说明需求或 Bug；`cat-plan` 会结合当前项目调查问题并形成一份可审阅、可继续修订的计划。审阅这份计划，就是在审阅 AI 的分析思路，比事后从代码改动中判断方向更快、更直接。

`cat-plan` 负责调查、纠偏、设计和计划；`cat-code` 只在你明确要求实施且范围已经闭合时修改和验证，并在需要新设计或扩大范围时停下来说明问题。

Associate Cat 是一套面向软件开发的通用 AI Skills，覆盖 AI planning、软件规划和范围受控的代码实施。它把需求分析、Bug 调查、技术方案、任务拆分与验证组织成基于项目事实的 coding agent workflow。

## 为什么选择 Associate Cat

- **从当前项目开始。** 两个 Skill 会先读取适用规则、代码、文档和验证入口，再形成判断。
- **少一些低价值来回。** `cat-plan` 主动调查可发现事实并收敛常规技术选择，只把目标、价值和风险相关的决定留给你。
- **从触点收敛相关范围。** 它从需求或症状出发，只继续调查会改变方案的职责、根因和依赖；不用为了一个局部问题，先把整个代码库都分析一遍。
- **流程与任务相称。** 你可以只分析而不实施，为复杂工作形成可交接计划，或直接处理一个小型且边界明确的修改。
- **审阅计划，而不是代码。** 写代码前就能确认 AI 的思路、方向、范围和验证是否靠谱，比事后从代码改动中判断更快、更直接。这里的“不审阅代码”只指不等代码写完才首次判断方向；实施后的验证和必要代码审查仍然不能省略。
- **边界明确，验证如实。** 规划不会自动授权写入；实施遇到新设计或范围扩张时会停止；交付只报告实际执行的检查。

**为什么也适合中大型游戏项目？** 这类项目的一个需求经常横跨运行时代码、编辑器工具、资源与配置、构建脚本和验证工程，相关逻辑还可能分散在多个模块里。`cat-plan` 不会因为仓库很大就先把整个项目全部分析一遍，而是从你提出的功能或 Bug 出发，先找到真正负责它的模块，再沿会改变方案的依赖、项目规则和验证路径继续调查。这样既能看到局部改动背后的关联，也能把无关系统留在范围外；实际效果仍取决于项目材料、模型和宿主能力。

Associate Cat 的公开发行版本及其文档，本身就是利用 Associate Cat 规划并完善的。

## 快速开始

使用以下命令安装两个 Skill：

```bash
npx skills add fengzizz/associate-cat
```

出现选择提示时，同时选择 `cat-plan` 与 `cat-code`。需要明确指定工作方式时，直接在请求中写出 Skill 名称。

如果希望为某个 Agent 全局安装两个 Skill 并跳过交互提示，请运行对应命令。以下命令只需选择一条。

适用于 **Codex**：

```bash
npx skills add fengzizz/associate-cat --skill cat-plan --skill cat-code -g -a codex -y
```

适用于 **Claude Code**：

```bash
npx skills add fengzizz/associate-cat --skill cat-plan --skill cat-code -g -a claude-code -y
```

适用于 **Cursor**：

```bash
npx skills add fengzizz/associate-cat --skill cat-plan --skill cat-code -g -a cursor -y
```

适用于 **Gemini CLI**：

```bash
npx skills add fengzizz/associate-cat --skill cat-plan --skill cat-code -g -a gemini-cli -y
```

适用于 **GitHub Copilot**：

```bash
npx skills add fengzizz/associate-cat --skill cat-plan --skill cat-code -g -a github-copilot -y
```

这些命令只指定安装目标，不表示不同模型和客户端中的行为完全一致。关键工作仍应在自己的环境中验证。

## 选择 Skill

| Skill | 如何工作 | 你会得到什么 | 停止边界 |
| --- | --- | --- | --- |
| [`cat-plan`](skills/cat-plan/SKILL.md) | 结合项目上下文校正需求或 Bug，调查相关事实，比较并收敛方案，再按任务需要形成设计、任务与验证计划。 | 分析、评审结论，或一份只保留当前有效内容、可继续反馈和交接的计划。 | 不修改代码、配置或资源；不替你决定业务语义、重大风险或范围扩张。 |
| [`cat-code`](skills/cat-code/SKILL.md) | 实施你明确要求且已经具备实施条件的计划或任务，或者边界清楚的直接修改，并执行相关验证。 | 实际修改、行为说明、验证结果，以及必要的阻塞与剩余风险。 | 不补新设计、不修改 Plan，也不静默扩大范围。 |

`cat-plan` 是这个工作流的核心：它先自行处理项目中可发现的事实和常规技术比较，只在业务语义、主观偏好、重大风险或范围扩张确实需要你决定时提问。普通分析不强制生成正式 Plan；复杂任务才需要把当前设计、任务、风险和验证维护在同一份当前计划中。Plan 与 Code 是两种责任，不是强制的两阶段仪式：可以只用 Plan 做分析，复杂工作再接 Code，小型且定义完整的修改也可以直接用 Code。

## 选择工作方式

1. **仅规划（Plan only）**——适合只需要分析、Bug 定位、方案、计划或评审而不要求实施的工作。

   ```text
   帮我看看这个需求应该怎么做，先用 cat-plan 把思路和计划整理成文档，暂时别改代码：……
   ```

2. **先规划后实施（Plan→Code）**——适合较复杂、存在设计工作或需要形成可交接实施边界的任务。

   ```text
   这个改动有点复杂，先用 cat-plan 结合项目看看怎么做，整理成一份可以直接实施的计划：……
   ```

   审阅计划后，可以补充意见：

   ```text
   这里不用...，直接复用现有的……就行，按这个思路把计划改一下。
   ```

   计划确认并具备实施条件后，再单独发送实施请求：

   ```text
   很好，用 cat-code 按这份计划实施。
   ```

3. **直接实施（Direct Code）**——适合修改目标、允许范围、预期结果和验证方式已经清楚，且不需要新设计的任务。

   ```text
   用 cat-code 帮我改一下这个问题：……。改动只需要……，完成后验证……。
   ```

对于一般问题，不需要预先写出完整的细节。说清楚需求或 Bug 现象，再加上自己的想法、希望的结果或不能改变的内容，就足够让 `cat-plan` 开始调查并生成计划文档。复杂任务建议把结果保存成文档，围绕同一份文档持续反馈；审阅计划就是在审阅 AI 的分析思路是否靠谱、后续实施是否符合预期，通常几轮沟通方案就能收敛，再单独交给 `cat-code` 实施。

## 核心边界

- **项目事实优先。** 两个 Skill 会先检查适用的项目规则、代码、文档和验证入口，再判断当前请求应如何推进。在用户限定的目标和范围内，`cat-plan` 会主动调查可发现事实并收敛常规技术选择，而不是把每个实现细节都交还给用户决定。
- **目标与风险由用户决定。** 业务语义、主观偏好、重大风险接受、破坏性取舍和范围扩张仍由用户决定。
- **维护同一份当前计划。** 同一活动规划任务只维护一份当前有效计划；持续反馈更新这份文档，不把普通修订历史混入实施范围。
- **计划做好不等于开始写代码。** 计划具备实施条件后，仍需你另外明确要求 `cat-code` 实施；不能仅凭计划文件或其中的文字推导写入授权。
- **停止而不是猜测，验证如实。** 如果事实冲突、缺少必要设计或必须扩大范围，`cat-code` 会停止并报告阻塞。结果只报告实际执行的检查，不把失败、阻塞或未运行的验证写成已通过。

Skill 由宿主 Agent 解释执行，实际表现可能随模型、客户端、权限和项目材料而变化；关键工作仍应在自己的环境中验证。
